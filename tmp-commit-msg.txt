security(rls): audit anonymous exposure on the live API and record the findings

Adds scripts/audit-anon-exposure.mjs (`npm run audit:anon`, also `npm run check:schema`
for the drift check). It probes the live PostgREST endpoint with the publishable key
only — no user JWT — and cross-checks the policies and function grants in the
migration file. Read-only: tables are queried with limit=1 and only row counts are
printed, never row content, so user data never reaches logs.

Findings (recorded as migration Section 99; deliberately no executable DDL there):

- Tables: 3 of 58 return rows to anon - user_answers (all is_public = true), 
  question_banks and question_bank_items. All three are the app's public-content
  paths (public notes / public question banks) and none of them exposes private
  data.
- Functions: 24 of 67 are anon-callable, because Supabase grants EXECUTE to
  anon/authenticated by default on new functions in the public schema - so the test
  is "was it explicitly revoked from anon", not "was it granted". Only one is in the
  genuinely risky class (anon + SECURITY DEFINER + no self-check): qr_login_status.
  Inspected and intentional: the pre-login scanner polls it and the gate is the
  secret_hash, not an identity; its sibling qr_login_claim is service_role only.
- Policies: 88 policies lack a TO clause and therefore apply to anon, but every one
  of them references auth.uid()/auth.role()/auth.jwt()/is_admin(), so none is a
  missing-authorization mistake.

Also recorded: 11 functions take p_user_id without checking p_user_id = auth.uid()
(get_plan_stats, get_subject_progress, get_review_count, get_review_pool_count,
get_kp_exclusion_stats, get_excluded_kp_questions, load_practice_session,
get_sessions_answered, get_type_accuracy, get_accuracy_change, get_daily_completion).
They are not exploitable today because they are SECURITY INVOKER and RLS still
applies, but the protection rests entirely on nobody ever switching one to
SECURITY DEFINER - which is the natural next step for cross-table reads, and would
turn all 11 into an IDOR at once.

No permissions were changed: only the publishable key was available, so the
anon / normal-user / admin three-identity comparison the review doc asks for could
not be run. Tightening anon access without that comparison would be betting on
production behaviour.
